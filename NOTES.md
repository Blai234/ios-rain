## Rain SE0 is GSI-only: GPI DMA path added — 2026-10-21

The fts9 boot (`pictures/IMG_0187`–`0196`) printed
`gsi-only clk=1 se0=0x4220 ifdis=0x1 cgc=0`: GENI_IF_DISABLE_RO bit 0 is
set, so SE0's FIFO interface is disabled in hardware and the CPU cannot
push bytes into it. Android's spi-geni uses GPI DMA for it. From the stock
DTB (`backup/rain-2026-10-19/vendor_boot_a.img`): `qcom,gpi-dma@4a00000`
(len 0x60000, `qcom,gpi-ee-offset` 0x10000, `qcom,gpii-mask` 0xf,
`iommus = <apps_smmu 0xf6 0>`), SE0 `dmas = <gpi 0 0 1 64 0>, <gpi 1 0 1
64 0>` (TX ch 0, RX ch 1, SE 0, proto SPI, 64 TREs). apps-smmu@c600000 is
`qcom,qsmmu-v500` with `qcom,skip-init`.

Patch 0082 now follows upstream Linux v6.6 `drivers/dma/qcom/gpi.c` and
`spi-geni-qcom.c` (copies in ignored `research/gpi/`): GPII registers at
base + off - 0x10000; GPII 0; interrupts configured but polled; event ring,
TX/RX channel allocate + start by polling the context CHSTATE; SE put in
GSI mode (DMA_MODE_EN, GSI_EVENT_EN 0xf, SE_IRQ_EN 0); each transfer is
RX DMA TRE + TX CONFIG0 (8-bit, packed, XO/4) + GO (duplex, CS0, LINK) +
DMA (IEOT); completion = TX xfer-complete event code 2. One 16 KiB
contiguous page holds the rings and buffers (physical addresses).
SMMU: reads sCR0/SMRs/S2CRs for SID 0xf6; with `rainftssmmu=1` (now in the
touch variants) it writes a bypass S2CR/SMR if the stream would fault.
Repeat lines: `<stage> gpi=<c> smmu=<c> scr0 idx s2cr pa was=` and
`<stage> gsnap ch= ev= rp= glob= gpii= err= type= evt=`. gpi stages:
m memory, s SMMU refused, r reset failed, e event ring, 0/1 ch alloc,
2/3 ch start, k ready. smmu modes: P disabled, B/U bypass, T translate,
F/u fault, b bypass programmed, N no free SMR, W write did not stick.

## The touch driver rebooted the phone three times: the TLMM tiles — 2026-10-20

Every touch boot ended with the phone rebooting into the recovery, and it
did so even when the driver only *read* the registers. The cause is the
TLMM layout: the device tree's `pinctrl@400000` is **not flat**. The
number selects a tile and the pin sits at `tile + number * 0x1000`, and
on this SoC (the bengal pinctrl driver,
`drivers/pinctrl/qcom/pinctrl-bengal.c`) the tiles are

| tile | offset | pins |
| --- | --- | --- |
| (unused) | `0x000000` | none |
| WEST | `0x100000` | 0-7, 12-17, 65-71, 80-86, 89, 92-97 |
| SOUTH | `0x500000` | 72-79, 98-112 |
| EAST | `0x900000` | 8-11, 18-64, 87-88, 90-91 |

The driver's first guess (`0x400000 + pin * 0x1000`) landed in the unused
tile, and reading an unimplemented register aperture on a Qualcomm SoC
raises an SError abort, which takes the kernel down. The touch's pins
are all in WEST, so the base is `0x500000`:

| pin | address | function |
| --- | --- | --- |
| GPIO 0-3 | `0x500000`..`0x503000` | qup0 (the SPI pins) |
| GPIO 80 | `0x550000` | the interrupt |
| GPIO 86 | `0x556000` | the reset |

The board's own `khaje-pinctrl.dtsi` confirms the touch lines: GPIO 86 is
`ts_reset` (drive strength 8 mA, pull up when active) and GPIO 80 is
`ts_release`. Note that the device tree's drive strength is in mA while
the register field is a three bit encoding, which is a second reason the
first driver's `drive = 8` was wrong: it set the output enable bit
instead and turned the interrupt pin into an output.

The driver now reads the pins at their real addresses, and the serial
engine programming and the transfers are still behind `rainftstx=1`.

## Rain display geometry: the canvas/framebuffer mismatch (2026-10-20, latest)

The phone has never swapped a frame to the panel: `sweetfb_noconsole=1` is set,
so the console still drawing means no AppleCLCD swap happened. The cause is
now identified in the source.

**Observed in the source.** `tools/mkadt.py` gave the Rain device tree the
canvas of the physical panel (`720x1650`), while `SweetFramebuffer.cpp`
(patch 0061) always presents the **iPhone X** size to the userland:

which is the case on Rain. `GetDisplaySize` therefore returned `1125x2436`

the lookup never happens and the GUI comes up.

is real in the source, and the scaler lookup is real on the phone, but no Rain
boot has been made with the canvas fixed yet.

### The real constraint: XNU only manages 1 GiB on Rain

`osfmk/arm64/arm_vm_init.c` sets `gPhysBase = args->physBase` and
`real_phys_size = args->memSize`, and `gPhysSize = mem_size =
(gPhysBase + args->memSize) - gPhysBase`. **The VM manages exactly the
window the boot arguments declare, and nothing else.** Sweet declares
3.95 GiB, topaz 4 GiB; Rain declared 1 GiB.

That 1 GiB also has to hold the kernel image, the zone map, the page
tables and the volatile UFS overlay, which is allowed to grow to 512 MiB
(`COW_MAX_BLOCKS` in `0082-zrain-ufs-cow.patch`). The iOS 16 userland was
therefore starting with at most a few hundred MiB, which is the most
plausible reason the boot never reaches the lock screen.

is needed:

- `tools/mkadt.py`: the Rain window is now `0x83000000 + 0x6d000000`

### The 1744 MiB window hung the kernel — the base was not twig aligned

The boot with `0x83000000 + 0x6d000000` never got past the shim: the
screen stayed on the red diagnostic console, with no XNU output at all
(not even the `SWEET EARLY` stage markers), and the phone stayed alive
(out of fastboot and adb), so the kernel hung or panicked before the
console existed.

**Cause.** XNU's physical aperture slides on 32 MB "twig" boundaries:
`arm_vm_physmap_slide` gives every PTOV entry a VA whose offset inside
its twig equals the offset of its PA inside its twig, and the whole
scheme only lines up when `gPhysBase` is twig aligned. The old window
(`0xb0000000`) was 32 MB aligned; `0x83000000` is only 16 MB aligned, so
the aperture was built half a twig off and the kernel never came up.

Fixed: the base is `0x80000000` (32 MB aligned, still above the shim
Image at `0x40080000-0x42220000`) and the window is
`0x80000000 + 0x70000000` = 1792 MiB, ending at the same `0xf0000000`
as before.

- `shim/loader.c` and `tools/validate_rain_payload.py` now reject a
  window whose base is not twig aligned, so this cannot be booted again.
- `tools/mkadt.py`, `tools/validate_rain_payload.py` and
  `tools/check_rain_memory.py` carry the new window; the tools take
  `--base`/`--size` so a window can be bisected without editing files.

The images for the aligned window are in `xnu/out-rain-ci/bisect/`
(`rain-display-crop-aligned-shim/shim-boot.img` and the scaled and

### cpus=4 is viable again: the GIC was never the problem — 2026-10-20

`cpus=4` was abandoned after the four-CPU boots corrupted the HFS
catalog, but the CPU start path is sound:

- The shim's `gold_gicr_prepare()` already prepares the redistributors of
  the three secondary Gold cores: it wakes each one (GICR_WAKER), sets
  GICR_IGROUPR0, the priorities and **enables the timers and SGI1** in
  GICR_ISENABLER0. The shim screen shows it: `GICR+ aff=00000101
  en=000C0002` for 0x101, 0x102 and 0x103. Its comment names the exact
  symptom it avoids: "without it a thread whose wakeup timer is armed on
  a secondary never wakes (backboardd stuck in usleep())".
- Rain's real MPIDRs are `8000000n` and `8000010n` (Qualcomm puts the
  cluster in Aff3), but the device tree keeps topaz's `0x100|n`
  encoding and that still works: Qualcomm's PSCI accepts it for CPU_ON,
  and the GIC's SGI Aff2/Aff3 filters are "any", so only Aff0/Aff1 have
  to match.

So the four-CPU failure is not the CPU start. The best explanation left
is the **volatile overlay**: `0082-zrain-ufs-cow.patch` stores whole
4 KiB blocks (`COW_MAX_BLOCKS 131072`, 512 MiB), while HFS writes
512-byte sectors, so the overlay fills eight times too fast. A write
refused at the limit in the middle of a catalog update leaves the
catalog inconsistent, which is exactly "HFS B-tree offset #0 invalid
(0x0000) ... followed by hfs_mark_inconsistent". The one-CPU boot hit

## Hardware facts (live DT + shim measurements)
- Framebuffer (ABL cont splash): 0x9c000000, 1080x2400, stride 4320, a8r8g8b8, panel is DSC *video* mode (no kick needed).
- RAM: 0x80000000+2G, 0x100000000+0xfcc00000. Live reserved-memory = PixelOS base dtb + sweet dtbo fixups.
- GICv3: GICD 0x17a00000, GICR 0x17a60000 (stride 0x20000, 8 PEs). GICD_TYPER 0x007B041D: SecurityExtn=1 (DS=0).
  ABL leaves GICD_CTLR = 0x10 (ARE_NS on, groups off). Writing 0x13 reads back 0x12: EnableGrp1A (bit1) is the one that matters.
- GIC Group 1 VERIFIED (shim 2c): vtimer INTID 19 = 30 IRQs/300ms, ptimer INTID 18 = 30, SGI 1 to self = 10/10.
  ICC_SRE=1 already, ICC_CTLR 0x8440, priority/enable writes stick. GICR_IGROUPR0 and GICD_IGROUPRn read 0 from NS
  even though Group 1 delivery works (RAZ in NS view) - do not use them as a health check.
  INTID 28 shows pending constantly (unknown PPI 12).
- Timer 19.2 MHz. Qualcomm PPI numbering: secure-phys/phys/virt/hyp = PPI 1/2/3/0 -> vtimer INTID 19, ptimer 18 (NOT 27/30).
- PSCI 1.1 via SMC, SMCCC 1.1. CPU_ON ok; SYSTEM_SUSPEND and SYSTEM_RESET2 unsupported.
- SMP: CPU_ON works for all 7 secondaries (MPIDR 0x81000n00).
- Entry EL1, MMU off, x0 = DTB (magic ok). ID_AA64MMFR0 = ...101122: 16K granule YES, 4K YES.
- No serial console: debug UART SE is in SPI mode on sweet. Screen is the only debug channel.

## XNU implications
- XNU GICv3 path (pexpert/arm/pe_fiq.c, VMAPPLE) puts the timer (PPI 27) in Group 0 = FIQ. With SecurityExtn=1,
  Group 0 is secure -> impossible from NS EL1. Need: Group 1 IRQ, ICC_IGRPEN1, INTID 19, and the timer handled in the IRQ path.
- XNU VMAPPLE PSCI uses `hvc`; sweet needs `smc`.
- PocketDarwin NonAppleGenericCpu.patch only swaps -mcpu=apple-h7 for -march=armv8-a.

## XNU loader design notes (xnu-8796)
- Entry: `_start` -> `start_first_cpu`, x0 = boot_args (PA), MMU off, EL1. boot_args: Revision/Version 2,
  virtBase/physBase/memSize/topOfKernelData, Boot_Video (fb 0x9c000000, rowBytes 4320, 1080x2400, depth 32),
  deviceTreeP/Length (ADT), CommandLine[608], bootFlags, memSizeActual.
- start.s maps [kernel mach header .. physBase+memSize) with cacheable BLOCKS. On Qualcomm every XPU carve-out
  must therefore lie below the kernel: use physBase = 0xb0000000 (above ramdump_fb 0xaf000000+16M,
  cdsp_sec, qseecom), end before rmtfs 0xfde01000 -> memSize ~0x4d000000 for bring-up.
- Base ADT: iPhone 8 d20ap DeviceTree from iOS 16.7.16 IPSW (tools/remotezip.py + tools/adt.py; LZFSE payload).
  Template values are empty: the loader must fill chosen/*, memory-map, cpu*/reg etc. like iBoot.
- XNU build: GitHub Actions (dipa-studio/ios-sweet, xnu.yml) via blacktop/darwin-xnu-build, MACOS_VERSION=13.5.
  New-clang fixes in xnu/patches; Xcode 16 iig is incompatible (IORPC.kernelContent) -> macos-14 runner, oldest Xcode.

## Kernel architecture plan (SWEET machine config)
- First stock build (VMAPPLE) is arm64e (PAC). Kryo 470 = ARMv8.2, no PAC -> SWEET must build plain arm64
  (HAS_APPLE_PAC is only defined for __arm64e__, so arm64 drops PAC automatically).
- Template: VMAPPLE (16K pages, GICv3 code in pe_fiq.c) minus APPLEVIRTUALPLATFORM hypercalls/paravirt PAC,
  plus BCM2837 (generic ARM: no APPLE_ARM64_ARCH_FAMILY Apple sysregs). Do not link the KDK lib<cfg>.os.*.a.
- Timer: XNU expects it on FIQ (sleh_fiq -> rtclock_intr). SWEET: GIC Group 1, so sleh_irq must ack ICC_IAR1,
  route INTID 19 to the same timer path, SGIs to cpu_signal_handler, EOI via ICC_EOIR1.
- SMP/interrupts: open-source AppleARMSMP (USE_APPLEARMSMP) needs an IOInterruptController (AIC role) and an
  IOPMGR (CPU power -> PSCI CPU_ON via SMC). Plan: built-in IOKit classes (SweetGIC, SweetPMGR, platform
  expert) compiled into the kernel and matched via iokit/KernelConfigTables.cpp -> no closed kexts needed.
- Debug: xnu patch 0003 sweet-fbcon = kprintf drawn on the framebuffer (ADT node "sweet-fbcon").
- ADT /arm-io ranges must not map to parent 0 (pe_arm_get_soc_base_phys()==0 disables serial): use parent 0x1000000.
